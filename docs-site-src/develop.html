Add a rule: one real check, end to end

A rule is a check plus a test that shows the check can fail. This section walks check 28, the token budget. It touches four files.

The four parts are the guard section, the reject-case test, the registry row and the mistakes row. The blocks below are read from the real files.

1. The guard section

The consistency guard is scripts/audit/consistency.ts. Each check is a numbered section that starts with // --- N.. A section pushes a message to the error list for each problem.

2. The reject-case test

The test plants a bad input and expects the guard to fail. A guard that no test can fail is a wish.

The title of the test starts with the check number. The mistakes row names this title. A test checks that the title exists.

3. The registry row

scripts/audit/checks-registry.json is the one list of checks. A row holds the rule, the fix, a real message and the source file. The CI checks page renders it.

scripts/audit/checks-registry.test.ts fails when the registry and the guard disagree. Check numbers must not repeat or skip one.

4. The mistakes row

A row in docs/mistakes-to-rules.md ties the mistake to the rule and the test.

See all rows on the Mistakes page.

The same steps as a list

  1. Write the reject-case test. Watch it fail.
  2. Add the numbered section to the guard. The test passes.
  3. Add the registry row with a real message.
  4. Add the row to the mistakes file.
  5. Run the audit commands below.

How the ratchets work

A ratchet is a number or a list that may only improve. CI compares it with the base branch. A pull request that makes it worse fails.

  • The baseline files hold known findings. A baseline may shrink. It never grows.
  • The script plugin/bootstrap/guards/ratchet.mjs compares a baseline with its base ref. It also fails on more findings of one kind.
  • A kind is the rule, the message and the file name without directory or extension.
  • The token budgets move in both directions. A file over its budget fails. A file well under its budget fails too, until you lower the budget.
  • The suppression count may not rise. A reviewer must accept a rise.

CI runs the ratchet script once for each baseline. This is the line for the zanity baseline.

To lock in a gain after a trim, run node scripts/audit/token-budget.ts --update-baseline and commit the new file. Never run an update command to add findings.

The source of this section is docs/development.md. The sections are "zanity and its baseline", "Message actionability" and "Token budget".

Keep client data out

The core must never name a client. The hook .githooks/pre-commit runs scripts/leak-guard.sh. The hook .githooks/pre-push runs gitleaks on the commits you push.

The guard reads a denylist of client terms from your machine. The list is never committed, because the list itself is client data.

Enable the hooks once for each clone. This line is read from docs/development.md.

CI cannot run the leak guard, because the denylist exists only on your machine. CI runs the self-test of the guard and gitleaks.

Cursor

Cursor follows the same rules and guards as Claude Code in this repository.

  • AGENTS.md holds the rules. Cursor reads it natively.
  • .cursor/rules/repo-rules.mdc is an always-on rule that only points to AGENTS.md.
  • .cursor/hooks.json runs two adapters from scripts/cursor/ over the two plugin hooks.

The shell adapter fails closed. A malformed payload gives a deny. The source is the section "Cursor" of docs/development.md.
