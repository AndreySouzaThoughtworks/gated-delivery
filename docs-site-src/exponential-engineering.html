Exponential engineering

This repository applies ideas from exponential engineering. This page credits the source and shows each mechanism with its proof and its gaps.

The ideas on this page are not ours. Exponential engineering comes from Ben O'Mahony and Fabian Nonnenmacher. Their site explains each idea in full. This page only shows how this repository applies them.

The authors also publish the source repository of the site and two tools. zanity is a rule checker for code. overwatch is a Claude Code plugin that hands failing checks back to the agent.

Each section below has four parts. The idea is our short paraphrase. How this repo applies it names real files. Proof shows numbers and output that the build reads from the repository. Where it falls short names a gap.

The build fails when a section cites a file that does not exist. No person types a count on this page.

The idea
Do not fix one mistake. Write a deterministic check that catches every future version of it. Each rule adds to the earlier ones, so quality compounds.
How this repo applies it
  • docs/mistakes-to-rules.md lists mistakes that happened here. Each row names a category, the rule that catches it and a test of that rule.
  • scripts/audit/mistakes-table.test.ts fails when a row names a file, check, zanity rule or test title that does not exist.
  • The rules run as {{checks}} numbered checks. scripts/audit/checks-registry.json holds the rule, the fix and a real failure message of each one.
Proof

The table holds {{mistakesCaught}} mistakes that a rule catches. It holds {{mistakesOpen}} more that no rule catches yet. Here is one real row.

Where it falls short
  • A person still spots the mistake and writes the rule. Nothing automates that loop.
  • The checks run in CI. Two git hooks run the leak guard and gitleaks. The repository sets up no language server or file watcher of its own.
  • The repository holds no overwatch settings file, so the watcher idea is not applied here.
The idea
Agents copy the patterns they see in a repository. A good pattern spreads. A bad one spreads too. A repository with no rules drifts the wrong way.
How this repo applies it
  • Agents once added assertions that could not fail, only to satisfy a rule. scripts/audit/assertion-effectiveness.ts now fails any assertion that no test makes fail.
  • Docs once drifted from the files. Check 5 in scripts/audit/consistency.ts compares doc counts with the real inventory.
  • The site build rejects a hand-typed count. scripts/site/gates.ts holds that gate.
Proof

Two real rows of the mistakes table show the drift.

Where it falls short
  • These checks find counts, paths and assertions that cannot fail. They do not find a sentence that is false in another way.
  • A reviewer still reads the text.
The idea
Agents come and go. A prompt or a memory belongs to one agent. Types, lint settings, tests and CI belong to the repository, so every agent gets them.
How this repo applies it
  • main requires {{requiredChecks}} status checks. docs/development.md lists them.
  • plugin/hooks/guard-bash.mjs denies a small set of destructive shell commands. It uses no model. plugin/hooks/lib/guard-core.mjs blocks the command when the guard cannot read its input.
  • scripts/leak-guard.sh runs from .githooks/pre-commit. .githooks/pre-push scans the pushed commits with gitleaks.
  • AGENTS.md is the one source of the repository rules. .cursor/hooks.json sends the Cursor hooks to adapters in scripts/cursor, so a second agent meets the same guards.
  • plugin/bootstrap/plan.mjs plans the same guardrails for a client repository. It writes nothing until you confirm each group.
Proof

The build reads this table from docs/development.md.

Where it falls short
  • The build and CI do not ask GitHub for the real branch settings. Only tests/live-gh.test.sh compares them with the table. The maintainer runs that test by hand.
  • The bash guard is an accident guard, not a security boundary. Its own header says that indirection defeats it.
  • The skills and agents of the plugin run in Claude Code only. The repository checks do not depend on any agent.
The idea
No single check catches every bug. Stack checks whose gaps sit in different places. A bug that passes one layer then meets the next.
How this repo applies it

The idea
A blocked agent reaches for an escape hatch. It adds an ignore, loosens a config, skips a test or deletes an assertion. Add rules that stop the rules from getting weaker.
How this repo applies it
  • Check 8 fails when zanity.toml stops selecting every rule, widens a disable list or excludes more than fixture folders.
  • plugin/bootstrap/guards/rules-about-rules.mjs does the same job in client repositories. It also fails an action pinned to a tag and a disabled overwatch.
  • The zanity rule relaxed-check exists in zanity, and select = ["all"] turns it on.
  • scripts/audit/suppressions.ts rejects a suppression with no reason. An assertion-density ignore must start with a code from scripts/audit/suppression-reason-codes.ts.
  • Check 17 and scripts/audit/assertion-effectiveness.ts reject assertions that cannot fail.
  • Check 27 pins each load-bearing rule line of an instruction file to a literal anchor in scripts/audit/rule-inventory.ts.
  • Check 29 keeps one audit job with one matrix, so a Node job cannot lose a step.
  • .github/CODEOWNERS routes zanity.toml, .github/ and scripts/audit/ to the maintainer.
Proof

The build also counts every suppression by its coded reason.

Where it falls short
  • The repository holds {{suppressionTotal}} suppressions. That is a large number to defend.
  • The count file is a cap, not a ratchet that forces the number down. A pull request may raise it, and the maintainer must accept the rise.
  • A coded reason shows that someone explained the suppression. It does not show that the explanation is true.
  • This repository does not run plugin/bootstrap/guards/rules-about-rules.mjs on itself. Check 8 and the checks above do that work.
The idea
Turn on every rule at its strictest setting. Let a warning fail the build. A warning that people tolerate teaches the agent to ignore warnings.
How this repo applies it
  • zanity.toml selects every zanity rule. CI runs zanity with --fail-on warning --strict, so a warning fails the build.
  • The zanity baseline holds {{zanityBaseline}} findings. Any finding fails.
  • tsconfig.json turns on strict and the unused-code flags. Check 23 fails when one turns off.
  • .shellcheckrc enables every shellcheck rule. CI runs shellcheck at the style level. CI runs zizmor in its pedantic mode.
Proof

Where it falls short
  • The source asks for static analysis every day. CI here runs on each pull request and each push to main. No scheduled run exists.
  • Some debt is tolerated and frozen. The message baseline holds {{messageBaseline}} old messages. The repository holds {{suppressionTotal}} suppressions.
The idea
A long instruction file loads in every session. An error message arrives only when the mistake happens. So the message should say what is wrong and what to do instead.
How this repo applies it
  • Check 32 reads every failure message in the scripts, hooks and audit tools. A message must name the value, state the rule and end with a fix. The limit is 40 words.
  • The tests of each guard judge its real output with assertActionable. That helper lives in plugin/scripts/run-cli.test.support.mjs.
  • The check fails a new message that is not actionable. It also fails a baseline entry that is now actionable.
Proof

The first message baseline held 243 messages, when the check arrived. It holds {{messageBaseline}} today. The check fails any pull request that makes it longer. This card shows the rule with a real failure message.

Where it falls short
  • {{messageBaseline}} old messages still fail the rule. They sit in the baseline.
  • The judge is a pattern proxy. It cannot tell whether the fix in a message is right.
  • The rule does not ask a message to point to a page that explains more.
The idea
Someone has already written a rule for most mistakes. Turn that rule on first. Write your own only for a gap that no tool covers.
How this repo applies it
  • zanity checks code patterns. The audit workflow pins it to one release by full commit SHA.
  • typos checks spelling and lychee checks links. Both run from .github/workflows/docs.yml.
  • shellcheck, actionlint and zizmor run from .github/workflows/static.yml. gitleaks runs from .github/workflows/gitleaks.yml.
  • plugin/bootstrap/install-zanity.mjs and plugin/bootstrap/pins.json install zanity into a client repository at a pinned release.
  • The plugin prints the overwatch install line and does not install overwatch.

Custom rules fill the gaps that these tools leave. They make up the {{checks}} numbered checks.

Where it falls short
  • The source lists ruff rules for Python. This repository is TypeScript and JavaScript, so ruff does not apply.
  • The zanity rules swallowed-error and skipped-test exist, and select = ["all"] turns them on. This repository has not checked whether zanity covers the other three mistakes in the source table.
  • The source also shows ast-grep. This repository does not use it.
The idea
Freeze the old violations and block every new one. Lower the limit whenever the count falls. No big cleanup is needed.
How this repo applies it
  • plugin/bootstrap/guards/ratchet.mjs compares a baseline with the same file at the base ref. It fails when the list grows, or when one kind of finding grows.
  • Three baseline files use it: the zanity, message and assertion baselines.
  • scripts/audit/suppressions.ts fails when suppressions outnumber the count in scripts/audit/suppressions.count. It also fails when the count falls and the file keeps the old number. That locks in the gain.
  • Check 28 fails when an instruction file grows past its budget in evals/token-budget.json.
Proof

The build reads the table from the repository.

The assertion baseline held 315 findings when it began (commit 52a7731). It holds {{assertionBaseline}} now. The build also ran the ratchet on a baseline that grew.

Where it falls short
  • The ratchet needs a base ref. CI runs it on pull requests only.
  • The message baseline still holds {{messageBaseline}} findings.
  • A budget can rise in a pull request that says why.
  • A ratchet counts findings. It cannot judge whether a rewritten finding is a good one.

Ideas this repository does not apply, or applies in part

  • Property tests and deterministic simulation. None exist. package.json lists no test library. A rounding bug or a retry race would reach review.
  • Rules in a language server or watcher. zanity offers a language server. This repository configures none. The overwatch watcher is a companion that the plugin recommends.
  • Live evals. They are off. The repository holds {{tiers.live}} live stamps and {{tiers.static}} static stamps. A static stamp proves the tooling, not the model. See Eval tiers.
  • A message ratchet that reaches zero. The message baseline still holds {{messageBaseline}} old messages.
  • No backlog. Applied in part. The slice skill plans small slices for one ticket and builds the next after a merge. It does not groom or order a backlog. The queue of tickets belongs to the client.
  • ruff and ast-grep rules. Not used. The repository has no Python code.
