Features

Each card shows one capability. It names the problem, the idea, how it works and why it beats a prompt.

Every card names the repository files that it comes from. The build fails when a card names a file that does not exist. The cards follow the order in which a ticket moves through the plugin.

Problem
Everyone prompts the AI in a different way. The same ticket gives a different result for each person.
Idea
Write the method down once, version it and share it like code.
How it works
  • The plugin ships {{skills}} skills, {{agents}} agents, {{commands}} commands and {{hooks}} hooks.
  • A person installs it from the marketplace: claude plugin marketplace add andrey1souza/gated-delivery.
  • The plugin has no version field. Each commit on main is an update.
Why it beats a prompt
A good prompt lives in one head. A skill lives in the repository, where the team reviews it. One fix reaches everyone on the next update.
Problem
The AI builds exactly what the ticket says. A vague ticket gives confident, wrong code.
Idea
The ticket is the first spec. Write it well before anyone codes.
How it works
  • It picks the kind first: Story, Task, Bug or Spike. Each kind has its own template.
  • A script lints the draft before the skill shows it.
  • A guardrail scan checks for secrets and personal data before any write to the tracker.
  • Every tracker write waits for your approval of the full text.
Why it beats a prompt
A prompt fills the gaps of a ticket with guesses. The skill picks the kind, lints the draft and scans it before it writes.
Problem
Between planning and kickoff, the context changes. The ticket does not.
Idea
Check that the ticket is still true before you build it.
How it works
  • It takes the date of the last edit of each acceptance criterion from the ticket history.
  • It reads what came after: linked tickets, epic siblings, decision records, contracts, specs and merged pull requests.
  • It reports only what makes the ticket text wrong now, with replacement text.
  • It writes nothing until you approve the final text.
Why it beats a prompt
A prompt invents improvements for any ticket. When nothing drifted, the skill opens its report with No drift found.
Problem
Coding straight from a ticket traps the context in one chat. The AI guesses the missing requirements.
Idea
Plan first, then code. Agree the plan with a person.
How it works
  • It inspects the repository first. Each claim is verified, or it becomes an open decision.
  • It drafts the data contracts, the threats with a disposition each, the acceptance criteria and the open decisions.
  • It never invents a schema. A missing contract becomes an open decision.
  • For each criterion it names the laziest wrong code that would pass. Then it tightens the criterion.
  • It splits the work into an ordered Rollout of PR-sized slices.
  • It writes one file, and only after you sign off every section.
Why it beats a prompt
A prompt starts to code at once and finds the gaps on the way. The spec lists the gaps first.
Problem
One-shot prompts give huge pull requests full of unchecked assumptions.
Idea
Run the agreed plan in small steps. Check each step before it merges.
How it works
  • It reads the tracker, the spec, Git, the pull requests and the handoff to find where the ticket stands.
  • For each slice it claims a branch, sends batches to the executor and opens a draft pull request early.
  • At the end of the slice it runs the gates, marks the pull request ready and stops.
Why it beats a prompt
Stop at any time. Run /slice tomorrow, on another laptop or as another person. It resumes from the tracker, Git, the pull requests, the spec and the handoff.
Problem
One agent runs the work blocks one after the other. Independent work waits in line.
Idea
Independent work does not wait.
How it works
  • A wave holds the slices that the spec marks as independent. Each has its own branch, worktree and pull request.
  • A round holds the batches of one slice that do not build on each other. Each runs in its own batch tree.
  • The orchestrator picks the batch commits onto the slice in plan order.
  • At most three writers run at once.
Why it beats a prompt
A prompt has one working directory. Separate git worktrees mean that parallel writers never overwrite each other.
Problem
Two people, or two agents, take the same ticket. They work on the same slice, or one works while the other waits.
Idea
Give each shareable thing an owner: a slice, a test run, a note.
How it works
  • Claim. slice-claim.mjs pushes an empty claim commit with a create-only push. A second claim exits with code 4 and names the holder.
  • Verify lock. A machine-wide lock makes the test runs of parallel trees take turns.
  • Resume block. An actor writes only its own Resume block, however old another one looks.
  • Per-slice handoff. Each slice of a wave keeps its own handoff file. The close-out folds them in.
Why it beats a prompt
A plain push is no claim. The second push can succeed. A create-only push cannot.
Problem
AI context dies when a session ends, the chat is compacted or another person takes over.
Idea
Keep the working memory of a ticket in a file, not in a chat.
How it works
  • Each actor keeps one Resume block: branch, base, last verified step and next step. handoff.mjs write-resume stamps it.
  • Carry forward holds decisions, deferrals, assumptions and dead ends. It holds an entry only when losing the chat would lose information.
  • When the ticket ships, handoff.mjs close folds the per-slice files and leads with the outcome.
Why it beats a prompt
A chat forgets after it compacts. A file stays in the repository or in the notes repository. The next session or person reads it.
Problem
Each AI session codes in its own way. It can also jump into a side quest.
Idea
Separate planning from doing. The plan decides. The executor executes.
How it works
  • For each criterion it writes one failing test, then the smallest code that passes, then one commit.
  • It follows the documented conventions of the changed repository before the stack recipes.
  • A design question stops it. It returns BLOCKED with evidence in the notes file.
  • A script checks the spec and the tree before the dispatch. Another script audits the commits after it.
Why it beats a prompt
A prompt lets the model decide when to stop. Here a script audits the commit history of every batch.
Problem
One review cannot judge both the structure of the code and the acceptance of the work. An author also misses its own gaps.
Idea
Review the structure in the session. Review the acceptance in a fresh context.
How it works
  • In session. senior-review-lens applies lenses A to G to the diff: cohesion, table or inline, test pyramid, test realism, test descriptions, dead variants and type-system shift. It fixes clear problems.
  • When it runs. The lens runs after each batch when a slice has more than one batch. It also runs over the whole slice.
  • Fresh context. The code-reviewer agent sees only the diff range and the acceptance criteria. It runs the verify command itself and tries to break each criterion.
  • Verdict. It reports PASS, BLOCK or UNVERIFIED. It never edits project files.
Why it beats a prompt
"The tests pass" is a claim. The reviewer's own run is the evidence.
Problem
An instruction in a prompt is a request. The AI can forget it.
Idea
Move the critical rules out of the prompt and into scripts that Claude Code runs.
How it works
  • The plugin registers {{hooks}} hooks.
  • Before each Bash command, guard-bash.mjs denies a small set of catastrophic ones: a forced recursive delete of the root or home folder, a forced push to main or master, and a fork bomb.
  • After each Edit or Write, format-on-edit.mjs runs the prettier of the repository.
  • The Bash guard is an accident guard, not a security boundary. A command hidden behind a script passes it.
Why it beats a prompt
Claude Code runs the hook before the tool. For a command that the guard matches, the model cannot talk its way past it.

Turn-end checks come from overwatch

The plugin has no Stop hook. The overwatch plugin covers the end of a turn. We recommend it as a companion.

  • Its README says that it runs your project tests beside Claude Code and hands failures back at once.
  • It runs zanity beside the tests when zanity is on the PATH.
  • It keeps completion guarded while a check is red.

Install it with /plugin install overwatch --marketplace benomahony/overwatch. The onboarding guide shows the setup.
Problem
A team needs proof that a ticket is finished. An agent that says the tests pass is a claim.
Idea
Each criterion carries its own evidence.
How it works
  • It writes one self-contained HTML page that starts with the business value.
  • It pastes the evidence into the page: test output, an API response or a screenshot. A link alone is not evidence.
  • A criterion with nothing collected says "No evidence collected" in its row.
  • A lint script checks the page.
Why it beats a prompt
A reviewer reads the evidence on the page. A reviewer who doubts it can repeat the run.
Problem
The AI can code from what it assumes. Docs may be stale. A change may break a caller that nobody named.
Idea
Treat each claim as unverified until the repository proves it.
How it works
  • It names its depth first: a quick posture, or a full pass.
  • It marks each claim as verified or inferred.
  • It lists where code, docs and tests disagree.
  • It finds the callers of what you are about to change. A script checks that each cited line is real.
Why it beats a prompt
A prompt fixes the one place it was told about. The pass looks for the other callers that would break.
Problem
One person learns how a system works. Everyone else asks that person again and again.
Idea
Write the explanation once, with its sources, and share it.
How it works
  • It writes nothing until you sign off the outline.
  • It labels every factual claim as Verified or Inferred.
  • It produces one HTML file. A lint script checks the file.
Why it beats a prompt
A chat answer helps one person once. A primer is checked once and read by the whole team.
Problem
The lessons of a session vanish when the session ends.
Idea
Turn each real mistake into a check that rules out its whole category.
How it works
  • It drops each lesson by default. A lesson stays only with evidence and a mechanism.
  • It extends an existing check first. Else it adds a new check to CI and the watcher.
  • Prose is the last rung. It is for a rule that no machine can decide.
  • A check needs a failing example that proves it rejects the bad case.
  • It proposes. It never writes in silence.
Why it beats a prompt
A prompt gets one more warning after each slip. A check rejects the mistake every time.
Problem
A production issue pulls people toward a guess at the cause. The guess then steers the work.
Idea
Follow the evidence: reproduce, hypothesise, fix and add a regression test.
How it works
  • It reads the ticket, all comments and every attachment. It searches for similar tickets first.
  • It writes two to four hypotheses, each with a prediction that can fail.
  • It runs the single most informative probe, then narrows.
  • It records the findings in a local handover corpus.
Why it beats a prompt
A prompt names a cause early. The skill ranks the hypotheses and tests the top one.
Problem
Commit messages, pull request text and docs fill with padding and claims that nobody checked.
Idea
Run a pass over durable text before it lands.
How it works
  • A script finds the named phrases and exits with code 1. Each hit comes with a fix.
  • A read pass then checks construction, relevance and placement.
  • The skill says that a pass which stops at the script has not happened.
Why it beats a prompt
The script finds a named phrase every time. A prompt must remember the list.
Problem
A skill is text. Change one sentence and the AI may behave in a different way, with no signal.
Idea
Every skill ships its own tests.
How it works
  • Each skill has an evals.md file with scenarios and a block of deterministic checks.
  • The runner starts real claude -p sessions. It repeats each scenario twice by default. A baseline arm loads no plugin.
  • A static stamp runs no model. It proves that the scripts, the checks and the rule anchors of the skill are intact.
  • Today the plugin holds {{tiers.live}} live stamps, {{tiers.static}} static stamps and {{tiers.waived}} waived stamps.
Why it beats a prompt
A prompt has no test. A skill has a rule inventory, and deleting an anchored rule line fails a check. Live evals are off, so no stamp proves that a model follows a skill.
Problem
Tooling that one client paid for should not leak its names, links and secrets to another client.
Idea
Keep the method generic. Keep the details of each client with that client.
How it works
  • The plugin names no client. A skill reads each client fact from a section of the nearest CLAUDE.md.
  • In this repository, the pre-commit hook runs a leak guard. It fails a commit that holds a term from a local denylist. It fails closed when the denylist is missing.
  • CI cannot run that guard, because the denylist exists only on the maintainer machine. CI runs the self-test of the guard and a secret scan.
  • Each client gets its own Claude profile, with its own login, plugins, memory and history.
Why it beats a prompt
A prompt has no guard. The same skills run at every client, and only the settings change.
