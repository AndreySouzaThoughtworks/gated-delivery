Trust

This page shows what the project measures, how it measures it, and what it does not verify.

Every number below comes from a file in the repository. The build reads the files each time it runs.

Rule inventories

A rule inventory lists the load-bearing rules of one skill, agent or command. Each rule has a literal anchor: a phrase that must stay in the file.

Check 27 of the consistency guard fails when an anchor is gone. The repository holds {{inventories}} inventories under evals/rules. Together they hold {{rules}} rules for skills, agents and commands.

The kind stop marks a rule about stopping or blocking. The kind never marks a ban.

Mutation score

A guard that never fails proves nothing. So the project tests the guard.

scripts/audit/rule-inventory-mutation.ts deletes each line that holds an anchor. It runs the inventory check on every mutant. A mutant is killed when the check reports the missing anchor.

The build runs that script for every inventory. The table shows the live result.

Unprotected share

The last column counts the non-blank lines of the files that hold no rule anchor. Nothing guards those lines.

The share is high. The inventories pin the rules that carry the most risk. They do not pin each sentence.

An inventory proves that the text is present. It does not prove that a model follows the rule.

Token budget

Instruction text costs tokens in every session. So each instruction file has a budget in evals/token-budget.json.

Check 28 fails when a file grows past its budget. The file lists {{budgetFiles}} budgets that sum to {{budgetTotal}} estimated tokens.

The estimate divides the characters by four. It uses no tokenizer and calls no API. It moves with the text, which is all a ratchet needs.

Stamp tiers

A skill carries at most one stamp. The Eval tiers page explains the three tiers.

A static stamp says the tooling is intact. The scripts pass, the eval checks lint and the rule anchors are present. It does not say that a model follows the skill.

Suppressions

A suppression silences a lint rule for one line. Each one needs a reason of four or more meaningful words.

A suppression of the rule assertion-density must start with a reason code. The count may not rise without a reviewer. The committed count is {{suppressionTotal}}.

The coded rows come from a scan of plugin, scripts and tests. The total comes from scripts/audit/suppressions.count. The row for other markers is the difference.

Assertion effectiveness

An assertion that no test can make fail protects nothing. scripts/audit/assertion-effectiveness.ts finds such assertions.

It copies the tracked files to a temporary folder. It instruments each assertion in non-test code and runs the tests. It lists every assertion that no test made fail.

That run is slow, so the site build does not run it. The site shows only the size of the baseline file that holds the known findings. The row for assertion-effectiveness-baseline.json in the next table is that size.

Each file in the table is a ratchet. It may shrink. It may not grow. The Develop page explains how.

What is not verified

This project checks a lot. It does not check everything. Each limit below names its source.

Live model runs

The maintainer keeps live evals off. The evals workflow is dormant and is not a required check. The source is the section "Skill evals" of docs/development.md.

So the project does not show that a model follows each skill. It shows that the tooling around the skills works.

Scripts run against stubs

The tests of the plugin scripts run against a stub of gh. The stub answers as the real program is expected to answer.

One opt-in test calls the real gh against a private sandbox repository. It is tests/live-gh.test.sh. CI never runs it. It exits with code 64 unless GATED_DELIVERY_ALLOW_LIVE_GH=1 is set.

That test does not cover the limit of 100 review threads. It does not cover a real merge. The source is the section "Tests" of docs/development.md.

Platforms

The plugin hooks and scripts are Node files. Nothing in the repository says how they behave on Windows.

Other limits

  • The sentence check measures length only. It does not prove that prose is clear or true.
  • The message check is a pattern proxy. It cannot judge whether a fix is correct.
  • Some mistakes still depend on human review. The Mistakes page lists them.

Read each number on this page as a statement about the tooling. None of them says that a model behaves.
