1. What gated-delivery is

gated-delivery is a Claude Code plugin. It turns one tracker ticket into small slices of work. Each slice merges on its own.

The plugin has no client baked in. Your repository supplies the client facts in its CLAUDE.md. The facts cover the tracker, the commit convention, the verify command and the reviewers.

The repository is also the marketplace. The manifest at the root points at the plugin/ folder. The plugin ships 12 skills, 3 agents, 3 commands and 2 hooks.

This repository does more than ship the plugin. It also checks itself. A set of scripts and CI jobs keeps its own rules, docs and counts true.

Who should read what

  • A newcomer starts with the flow, then the worked examples.
  • A maintainer reads the guardrails, then the section on mistakes and rules.
  • A skeptic reads the limits first. They are honest.

2. The philosophy

The design follows exponential engineering. It has three working rules.

Harden the codebase, not the agent

An agent forgets, drifts and guesses. A repository does not. So the repository holds the guardrails.

Hooks, CI jobs and lint scripts run every time. They need no memory of earlier sessions.

Guidance is not a guardrail

A line in a prompt is a request. A model can ignore it. A script that exits with a non-zero code is a guardrail.

So the repo prefers a check over a sentence of advice. Each rule in this repository should be a deterministic check.

Test for any rule: can a script fail a pull request that breaks it? If not, treat it as a wish.

Every mistake becomes a deterministic rule

When a mistake happens, the fix is not a reminder. The fix is a check that rules out the whole category of mistake. A test proves that the check can fail.

The file docs/mistakes-to-rules.md records each mistake next to its rule and its test. A test fails when a row names something that does not exist.

3. The delivery flow

A ticket moves through four stages. Each stage ends in a gate.

Stage 1: spec

/gated-delivery:spec reads a ticket and drafts one spec. The spec has an ordered ## Rollout of PR-sized slices.

The skill holds drafts in the conversation. It writes nothing until you sign off each section. It then writes one file.

Stage 2: slice

/gated-delivery:slice implements the ticket slice by slice. Independent slices run in parallel worktrees. Each slice gets its own branch and pull request.

Inside a slice, the skill plans small batches. For each batch it dispatches a slice-executor agent. The executor writes one failing test, then the minimal code, then one commit per acceptance criterion.

Before each dispatch, executor-preflight.mjs checks the spec and the tree. After each batch, batch-audit.mjs audits the commits.

Stage 3: review gate

A slice is not done until three checks pass.

  1. Full verification runs the verify command of the client.
  2. senior-review-lens audits the structure of the change.
  3. The code-reviewer agent reviews the diff in a fresh context. It sees only the diff and the acceptance criteria.

The slice also stops while a review thread is open. pr-gate.mjs lists the open threads, including threads from review bots.

Stage 4: commit and pull request

/gated-delivery:commit makes one commit that follows the client convention. It stages files by explicit path.

/gated-delivery:commit-push-pr adds a push to an explicit refspec and opens the pull request. The skill never merges anything. You merge, then run /gated-delivery:slice again for the next slice.

Around the loop

  • /repo-forensics inspects code before a change exists. It never writes code.
  • /story-drift checks an old ticket against its linked records.
  • /issue-writing drafts and publishes tickets against a template.
  • /deskcheck renders finished work as an HTML walkthrough for a demo.
  • /primer researches a topic and renders an HTML explainer.
  • /prod-support guides the diagnosis of a production incident.
  • /learn-flow turns the mistakes of a session into proposed checks.
  • /audit-flow audits the flow itself and proposes trims.

Branch protection requires nine status checks on main, for admins too. The workflows are in .github/workflows/.

The consistency guard

The core is scripts/audit/consistency.ts. Its numbered sections are the true list of checks. It prints one error line per problem. Each line names the file and ends with a hint.

The checks fall into groups. Each group below shows one real failure message. We produced each one by running the script on a broken input.

Inventory and docs

These checks fail when the files and the docs disagree. A skill needs its files, its name and its row in the inventory. A count in the README must match the files.

ERROR README.md says "5 skills", which is not the actual count of 12. Hint: change it to "12 skills".

Manifests and versions

Neither manifest may pin a version. Without a version, Claude Code uses the commit SHA. So every commit reaches installs.

ERROR plugin/.claude-plugin/plugin.json carries a version. A pinned version freezes installed copies until someone changes it. Hint: delete the "version" field; users then get every commit.

Rules about rules

These checks stop anyone from loosening the other checks. They guard zanity.toml, the tsc flags, conditions that cannot vary and the numbering of the checks. They also limit which agents may pin a model.

ERROR agent "code-reviewer" pins model "opus", but is not allowed to pin one. Hint: pin a model only on the scout, since every other agent inherits the session model.

Rule inventories

Live evals are off. So nothing else notices when a text trim deletes a rule. A file in evals/rules/ lists the load-bearing rules of one instruction file. Each rule has a literal anchor.

Check 27 fails when an anchor is gone. It also fails when a marker line, such as one with never or STOP, has no rule. It scans the markdown files under plugin/skills/ that are not SKILL.md.

ERROR evals/rules/skill-slice.json: anchor "`/slice` never merges one" is in none of plugin/skills/slice/SKILL.md, plugin/skills/slice/references/parallel.md, plugin/scripts/slice-state.mjs, plugin/scripts/slice-cleanup.mjs, plugin/scripts/slice-claim.mjs, plugin/scripts/notes-repo.mjs, plugin/scripts/handoff.mjs, plugin/scripts/pr-gate.mjs, plugin/scripts/commit-plan.mjs. Hint: the rule line was deleted or reworded; restore it or update the anchor.

Token budget

Instruction text costs tokens in every session. evals/token-budget.json sets a budget for each instruction file. Check 28 fails a file that grows past its budget.

ERROR plugin/skills/slice/SKILL.md grew to 8994 estimated tokens, over its budget of 8000. Hint: trim the text, or raise the budget in evals/token-budget.json in a PR that says why.

The estimate is the number of characters divided by four. It uses no tokenizer.

Eval stamps

A changed skill needs a stamp for its current hash. The README states how many stamps are live, static and waived. See the eval tiers below.

Node floor

Check 31 fails when the Node floor reaches end of life, or when a document names another floor.

ERROR README.md says "Node 18 or later" but package.json sets the floor to Node 22. Hint: make the document and engines.node name the same release.

CI parity and live opt-in

Check 29 keeps the consistency steps in one matrix job. So consistency and node 26 cannot drift apart. Check 30 refuses a test that starts a real claude -p session without an opt-in.

tests/commit-convention.test.sh: refusing to start. Rule: a test that launches a real claude -p session spends your logged-in subscription, so it runs only on request. Fix: rerun with GATED_DELIVERY_ALLOW_LIVE_CLAUDE=1 to accept that usage.

Message actionability

A failure message must name the offending value, state the rule and end with a fix. It must have 40 words or fewer. Check 32 fails a new message that does not. The old messages sit in a baseline that only shrinks.

Docs style and the guide

Check 33 grades every document. The files are README.md, AGENTS.md, plugin/README.md, docs/*.md and this guide.

A file fails when fewer than 80% of its sentences have 20 words or fewer. The check ignores code blocks, inline code, tables, headings and link targets.

ERROR docs/onboarding.md has 67% of its 94 sentences within 20 words, below the 80% ASD-STE100 rule. Hint: split each long sentence, longest first: line 84 (22 words) "A red build can be one..."; line 96 (21 words) "Install step 0 keeps going with..."; line 98 (21 words) "Install step 1 keeps going with..."; line 100 (21 words) "Install step 2 keeps going with..."; line 102 (21 words) "Install step 3 keeps going with...".

Check 34 keeps this guide true. It fails when the guide is missing. It fails when the guide misses a skill, an agent or a command. It fails when a count is wrong. It fails when the README does not link the guide.

ERROR docs/guide.html does not name the agent "scout". Hint: add it to the guide.

Lint scripts

  • scripts/audit/comments.ts rejects a comment that tells the history of a change.
  • scripts/audit/suppressions.ts rejects a suppression with no reason. It also rejects a count that differs from scripts/audit/suppressions.count.
  • scripts/audit/jsdoc-types-only.ts rejects prose inside a JSDoc block.
  • scripts/audit/assertion-effectiveness.ts rejects an assertion that no test can make fail.
scripts/a.ts:1: rule temporal-contrast: "used to be slower". Hint: delete the before-and-after contrast, or restate what the code does now; a comment states a constraint the code cannot show, in the present tense

Hooks that run for you

The Bash guard denies catastrophic commands, such as a force-push to main. It fails closed. When it cannot read its input, it blocks the command.

Blocked by gated-delivery guard: force-push to main/master is not allowed in `git push --force origin main`; run it outside the agent or reword the command.

Git hooks in .githooks/ add a leak guard at commit time and a gitleaks scan at push time. Enable them once with git config core.hooksPath .githooks.

Cursor

Cursor follows the same rules. AGENTS.md is the one source of the repo rules. .cursor/hooks.json runs adapters over the same two plugin hooks.

6. The eval tiers

Each skill has an evals.md with scenarios and a fence of deterministic checks. A stamp in evals/results/ records the result for the current hash of the skill.

The three tiers of a skill stamp
TierWhat ranWhat it proves
liveReal claude -p sessions, graded by checks and a judge.The model followed the skill in those scenarios.
staticThe deterministic checks, the script tests and the rule anchors. No model runs.The scripts and checks of the skill are intact. Nothing about the model.
waivedNothing. A person wrote a reason.Nothing. The guard shows a warning.

Today, every skill carries a static stamp. No skill has a live stamp. The README states the true numbers, and check 25 keeps them true.

Any edit to a skill changes its hash. The old stamp then goes stale. Re-stamp the skill with this command:

node scripts/eval/changed-skills.ts --static slice

The command exits 0 when every check passes. It exits 1 when a check fails, and then it writes no stamp.

Do not run live evals unless the maintainer asks. They spend a subscription. The opt-in variable is GATED_DELIVERY_ALLOW_LIVE_CLAUDE=1.

7. How a mistake becomes a rule

This section walks through one real row of docs/mistakes-to-rules.md.

The mistake

The repository was public with no license. Nobody was allowed to reuse it. The category of the mistake is code that looks open but is not.

The rule

The row names check 24 of the consistency guard. The check fails when the license file is missing or empty. It also fails when the README does not link it. This is the real code:

if (!existsSync(licensePath) || read(licensePath).trim() === "") {
  errors.push(`${LICENSE_FILE} is missing or empty. Hint: add the license text; without one nobody may reuse the code.`);
} else if (existsSync(readmeFilePath) && !read(readmeFilePath).includes(`](${LICENSE_FILE})`)) {
  errors.push(`${README_FILE} does not link ${LICENSE_FILE}. Hint: add a License section that links it.`);
}

The test

A test must show that the check can fail. The row names this test: scripts/audit/consistency-repo-config.test.ts, titled "the repo must carry a license that the README links".

The test builds a valid fixture repo and runs the guard. It must pass. Then it blanks the license, deletes it and unlinks it from the README. Each case must fail with the expected message.

const blank = validRepo();
write(blank, "LICENSE", "  \n");
assert.match(runGuard(blank).out, /LICENSE is missing or empty/);

The guard on the table

scripts/audit/mistakes-table.test.ts reads every row. It fails when a row names a check, file, zanity rule or test title that is missing. So the table cannot rot.

Some mistakes have no rule yet. The second section of the file lists them with the reason. Honest gaps are part of the design.

8. Worked usage examples

Install

claude plugin marketplace add AndreySouzaThoughtworks/gated-delivery
/plugin install gated-delivery@gated-delivery
/reload-plugins

Install at user scope. Run /reload-plugins afterwards. Without it, the agents stay unregistered in the running session.

Update

claude plugin update gated-delivery@gated-delivery
/reload-plugins

The plugin has no version number. Every commit on main is an update.

Run a skill

Give the spec skill a ticket key. It reads the ticket and shows you its intent. It writes a file only after you sign off every section.

/gated-delivery:spec PROJ-202

Then run the slice skill with the same key. It plans the batches and asks you to confirm them. At the end it marks the pull request ready and stops.

/gated-delivery:slice PROJ-202

Commit with the client convention. List the files by explicit path:

/gated-delivery:commit

Add a rule and its reject-case test

This example is not in the repository. It shows the shape of a new check. Say that a skill description must stay short.

  1. Add a numbered section at the end of scripts/audit/consistency.ts, before the report. Use the next free number.
  2. Push a message that names the file, states the rule and ends with a fix.
  3. Add a reject-case test in the matching scripts/audit/consistency-*.test.ts file.
  4. Run the test. Make sure that it fails when the rule is broken.
  5. Add a row to docs/mistakes-to-rules.md that names the check and the test title.
// --- 35. A skill description stays short ---
const MAX_DESCRIPTION_CHARACTERS = 400;
for (const skill of skills) {
  const description = read(join(skillsDir, skill, "SKILL.md")).match(/^description:\s*(.+)$/m)?.[1] ?? "";
  if (description.length > MAX_DESCRIPTION_CHARACTERS) {
    errors.push(`skill "${skill}" has a description of ${description.length} characters, over the limit of ${MAX_DESCRIPTION_CHARACTERS}. Hint: shorten it.`);
  }
}
test("a skill description over the limit is rejected, one at the limit passes", () => {
  const dir = validRepo();
  write(dir, "plugin/skills/alpha/SKILL.md", `---\nname: alpha\ndescription: ${"x".repeat(401)}\n---\n`);
  const { code, out } = runGuard(dir);
  assert.equal(code, 1, out);
  assert.match(out, /skill "alpha" has a description of 401 characters/);
});
node --test scripts/audit/consistency-rules.test.ts

A new assertion in non-test code needs a test that can make it fail. The assertion-effectiveness tool checks this.

Run the audit locally

Run these commands from the repository root before you open a pull request:

npm ci && npx tsc --noEmit
env -u CLAUDECODE zanity check . --baseline zanity-baseline.json --new-only --agent --fail-on warning --strict
GATED_DELIVERY_BASE_REF=origin/main node scripts/audit/consistency.ts
node scripts/audit/comments.ts
node scripts/audit/suppressions.ts
node scripts/audit/token-budget.ts
node scripts/audit/asd-style-report.ts
node scripts/eval/run-checks.ts --lint

The test commands are in .github/workflows/audit.yml. Run them too.

The report script prints the share of short sentences for each document:

node scripts/audit/asd-style-report.ts

Add guardrails to a client repository

Run the bootstrap command in a Python or TypeScript repository on GitHub. It shows a diff first. It writes nothing until you confirm each group.

/gated-delivery:bootstrap

9. Node and version policy

  • The plugin has no version field in either manifest. Checks 15 and 19 reject a pinned version.
  • The plugin floor is the oldest Node release that still gets security fixes. Today that is Node 22.
  • Dev tooling needs Node 22.18 or later. That release strips TypeScript types.
  • CI tests Node 22 and Node 26, in one matrix job.
  • Check 31 fails when the floor reaches end of life. The dates are in scripts/audit/node-floor.ts.
  • Plugin code is plain JavaScript. It must not import TypeScript. Check 20 enforces this.

The license is MIT. The repository carries the license file, and the README links it.

10. What is not verified

This repository checks a lot. It does not check everything. These limits are real.

  • All skill stamps are static. No stamp is live. No test shows that a model follows a skill.
  • No live eval runs. They are off because they spend a subscription.
  • A rule inventory proves that the rule text is present. It does not prove that the rule keeps its meaning.
  • The plugin scripts have not run against a real gh. Their tests use fixtures and stubs.
  • The sentence check measures length only. It does not prove that the prose is clear or true.
  • The message check is a pattern proxy. It cannot judge whether a fix is correct.
  • Some mistakes still depend on review. The second table in docs/mistakes-to-rules.md names them.
  • The count of suppressions is visible and reviewed. It is not a ratchet.

A static stamp says that the tooling is intact. It never says that the model behaves.
